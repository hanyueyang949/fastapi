前端、API、后端、数据库之间是什么关系？

架构图解 · 「图书馆管理 API」项目 · FastAPI + SQLite + 原生 JavaScript

01全景：4 个层，3 次跳跃

每一层只和相邻的下一层说话，没有人可以跨层。

使用者 ① 人 —— 使用这个应用的人

点击、输入、按「保存」。他根本不知道有 API 这个东西存在。

鼠标点击 / 键盘输入 → 触发 JavaScript 事件

前端 ② 浏览器 —— http://127.0.0.1:5500

负责画界面，并决定向后端要什么数据。永远不碰数据库。

app.html · 结构 style.css · 外观 app.js · 行为 api.js · fetch()
HTTP 请求 POST /books/ + 请求体 {"title":"..."} · 文本格式的 JSON · 来源端口 :5500

边界 ③ 网络 —— 浏览器在这里执行 CORS 检查

浏览器自动加上 Origin 请求头，并要求服务器授权。CORS 报错就发生在这条线上。

到达 uvicorn · 文本被转成 Python 的 dict

后端 ④ FastAPI —— http://127.0.0.1:8000

接收、校验、执行业务逻辑、返回 JSON。它是唯一能读写数据库的东西。

main.py · 装配 + CORS routes/ · API（门面） schema/ · Pydantic 校验 controller/ · 业务逻辑 models/ · 表结构 database/ · 连接
SQL 语句（由 ORM SQLAlchemy 自动生成）

数据 ⑤ SQLite —— db.sqlite3

一个文件，里面是 books 表。即使服务器关掉，数据也不会丢。

旁路 · 文档
/docs 和 /openapi.json 是 FastAPI 读取 routes/ + schema/ 后自动生成的。 不是你写的：代码一改，它们自己就更新。
旁路 · 第三方 API
后端可以去调用外部 API（Open Library、Stripe、OpenAI…）。 必须由后端调用，绝不能从前端调，否则密钥会暴露。

02一次请求的旅程：13 站

真实场景：用户新建一本书。注意每一跳数据的「形态」都在变 —— 这正是很少有人讲清楚的地方。

  1. 用户在表单里输入浏览器
    此刻数据住在 DOM 里：<input value="El Quijote">
  2. JavaScript 把它收进一个对象app.js { title: "El Quijote", author: "Cervantes", page: 863, stock: 2 }
  3. 变成一段 JSON 文本api.js '{"title":"El Quijote","author":"Cervantes","page":863,"stock":2}'
    形态是字符串。网络只能传文本，传不了对象。
  4. 浏览器发出请求HTTP POST /books/ HTTP/1.1 Content-Type: application/json Origin: http://127.0.0.1:5500 {"title":"El Quijote","author":"Cervantes","page":863,"stock":2}
  5. 在此之前，先有一次 CORS 预检浏览器 OPTIONS /books/ → 200 OK access-control-allow-origin: *
    浏览器先问一句「我可以发吗」，才发真正的请求。这行代码不是你写的。
  6. uvicorn 收到文本并转换main.py dict: {"title":"El Quijote","author":"Cervantes","page":863,"stock":2}
    从 HTTP 文本变成 Python 对象。
  7. 找到正确的路由routes/ POST + /books/ → create_new_book()
  8. Pydantic 校验内容schema/ BookCreate(title="El Quijote", author="Cervantes", page=863, stock=2)
    如果 page <= 0 → 直接返回 422，后面什么都不执行。
  9. 业务逻辑构造出「表对象」controller/ Book(title="El Quijote", author="Cervantes", page=863, stock=2)
    ORM 对象：一条「未来的行」，此刻还没有 id。
  10. ORM 生成 SQL 并写入models/ + database/ INSERT INTO books (title, author, page, stock) VALUES (...)
  11. 数据库把 id 交回来db.sqlite3 id = 1 ← 由数据库生成，不是客户端发的
  12. 序列化成 JSON 并响应response_model HTTP/1.1 201 Created {"title":"El Quijote","author":"Cervantes","page":863,"stock":2,"id":1}
    201 = 资源创建成功。
  13. 浏览器把结果显示出来app.js res.json() → JS 对象 → 模板字符串 → innerHTML → 屏幕上的像素
    闭环完成：这本书立刻出现在列表里，页面没有刷新（R3）。

03那么……「API」到底是什么？

它不是第四个组件。它是后端的外门：前端唯一能看见的那一部分。

后端 —— 完整的程序（:8000 上的 Python 进程）

在服务器上运行的一切，都算后端。

API —— 门面与契约

routes/（有哪些路径和方法）+ schema/（接受和返回什么样的 JSON）。 这就是前端所知道的全部。

实现 —— 如何兑现这份契约

controller/（逻辑）+ models/（表）+ database/（连接）。 前端永远看不到这一部分。

如果你改了这里…前端要跟着改吗？为什么
controller 内部的逻辑不用契约没变，返回的东西还是一样
把 SQLite 换成 PostgreSQL不用只改 DATABASE_URL，ORM 抹平了差异
把 FastAPI 换成 Django不用（只要路由和 JSON 保持不变）API 是契约，不是框架
在 schema 里增加一个字段要契约变了，界面上得把它显示出来
把 page 改名成 pages要前端还在发 page → 直接 422

05三句话总结全部

1. 没有人跨层。
前端不和 SQLite 说话，后端不画 HTML。每一跳用不同格式：浏览器与服务器之间是 JSON，服务器与数据库之间是 SQL。
2. API 是契约。
只要 API 不变，你可以单独重写前端或后端。一旦 API 变了，两边都必须同步改。
3. 报错会告诉你哪一层坏了。
ERR_CONNECTION_REFUSED → 没有服务器。404 → 路径写错。422 → JSON 不合法。500 → 后端出错。CORS → 网络边界。
以及一个实用推论
如果屏幕上没显示出来，先去看 /docs。那里能成功 → 问题在前端；那里也失败 → 问题在后端。
